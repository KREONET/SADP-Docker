# 내부망 서버와 Cloudflare Tunnel

두 기능을 설명합니다.

1. **컨트롤러 라우팅**: 같은 내부망에 있는 워커 서버들의 트래픽을 컨트롤러(서버 id 0, PADED가 설치된 서버)의 프록시 하나로 받습니다.
2. **Cloudflare Tunnel (외부 트래픽)**: 공인 IP·열린 포트·DNS-01 자격 증명 없이 Cloudflare Tunnel로 도메인을 공개합니다.

사용 방법은 [README](../../README.md)의 해당 절에 있습니다. 이 문서는 동작 원리와 코드 위치, 문제 해결을 다룹니다.

## 1. 컨트롤러 라우팅

### 동작 원리

```
브라우저 ─▶ 컨트롤러 coolify-proxy (Traefik 또는 Caddy)
              │  (Docker 라벨을 읽음)
              ▼
            paded-relay-xxxx (nginx stream, 컨트롤러의 coolify 네트워크)
              │  TCP
              ▼
            워커 10.0.0.12:41000 ─▶ 앱 컨테이너 :3000
```

- 워커에는 프록시가 없습니다. `Server::isRoutedThroughController()`가 true이면 `proxySet()`과 `isProxyShouldRun()`이 false가 되고, `StartProxy`와 `CheckProxy`도 아무것도 하지 않습니다.
- 배포할 때 라벨 생성은 평소와 같습니다. 다만 도메인이 있는 컨테이너는 **워커 내부 IP에만** 호스트 포트(41000-48999)로 공개됩니다. 예: `10.0.0.12:41000:3000`.
- 컨트롤러에는 라우팅되는 컨테이너마다 릴레이 컨테이너가 하나 생깁니다. 릴레이는
  - 앱의 프록시 라벨을 그대로 갖고 있고(네트워크 라벨만 컨트롤러 네트워크로 바꿈),
  - 앱과 같은 컨테이너 포트(예: 3000)에서 받아 워커의 호스트 포트로 넘깁니다.

  그래서 컨트롤러의 Traefik/Caddy는 릴레이를 로컬 컨테이너처럼 라우팅합니다. 라벨을 프록시 설정으로 바꾸는 코드가 없어서 도메인, HTTPS, 와일드카드 인증서, Basic Auth, 접근 제한(내부망 전용, 로그인 전용)이 원래대로 동작합니다.
- 릴레이는 모두 컨트롤러의 Compose 프로젝트 `paded-relays` 하나에 들어 있습니다(`/data/coolify/proxy/controller-ingress/docker-compose.yml`). 동기화할 때마다 이 파일을 다시 쓰고 `docker compose up -d --remove-orphans`를 실행하므로, 없어진 라우트의 릴레이는 저절로 지워집니다.

### 라우트 상태 (`controller_ingress_routes` 테이블)

| 컬럼 | 뜻 |
|---|---|
| `server_id` | 워커 |
| `resource_key` | `application-12`, `application-12-pr-3`, `service-7` |
| `service_name` | 같은 리소스 안의 컨테이너 구분. 일반 앱은 항상 `application`이라 여러 워커의 같은 앱이 한 릴레이로 묶입니다. |
| `container_name` | 워커의 컨테이너 이름 (워커별로 유일) |
| `ports` | `{"3000": 41000}` 컨테이너 포트 → 워커 호스트 포트 |
| `labels` | 릴레이에 붙일 프록시 라벨 |
| `is_active` | 트래픽을 받는지 여부 |

- **롤링 업데이트**: 새 컨테이너는 새 호스트 포트로 비활성 라우트를 받습니다. 헬스 체크를 통과하면 `ControllerIngress::activate()`가 새 라우트를 켜고 예전 라우트를 지운 뒤 바로 동기화합니다. 그다음 예전 컨테이너를 멈추므로 끊김이 없습니다.
- **서비스**: 컨테이너를 그 자리에서 바꾸므로 시작할 때 바로 활성화됩니다.
- **정리**: 리소스가 삭제되면 모델의 `deleted` 이벤트가 라우트를 지웁니다. 동기화할 때도 리소스가 없거나, 다른 서버로 옮겨졌거나, 워커가 라우팅을 껐으면 라우트를 지웁니다.

### 코드 위치

| 하는 일 | 파일 |
|---|---|
| 포트 공개, 라우트 기록, 활성화, 릴레이 생성·동기화 | `app/Services/ControllerIngress/ControllerIngress.php` |
| 비동기 동기화 | `app/Jobs/SyncControllerIngressJob.php` |
| 켜기/끄기 (워커 프록시 정지·재시작) | `app/Actions/Server/ConfigureControllerRouting.php` |
| 화면 (워커: 설정, 컨트롤러: 목록과 동기화) | `app/Livewire/Server/Proxy/ControllerRouting.php` |
| 앱 배포 연결 | `ApplicationDeploymentJob::prepareControllerIngress()` / `activateControllerIngress()` |
| 서비스 연결 | `StartService::routeThroughController()` |
| 수동 동기화 | `php artisan paded:sync-controller-ingress` |
| 테스트 | `tests/Feature/ControllerIngress/ControllerIngressTest.php` |

## 2. Cloudflare Tunnel (외부 트래픽)

### 동작 원리

```
브라우저 ─HTTPS─▶ Cloudflare ─터널─▶ cloudflared (coolify-cloudflared-ingress)
                                        │ http://coolify-proxy:80
                                        ▼
                                      coolify-proxy ─▶ 앱 (또는 릴레이 ─▶ 워커)
```

- 토큰 방식 터널입니다. Public Hostname(어떤 도메인을 어디로 보낼지)은 Cloudflare 대시보드에서 관리하고, PADED는 cloudflared 컨테이너만 실행합니다. 와일드카드 Public Hostname 하나(`*.example.com` → `http://coolify-proxy:80`)면 도메인을 추가할 때마다 Cloudflare를 다시 만질 필요가 없습니다.
- TLS는 Cloudflare가 끝내므로 프록시는 **HTTP로만** 서비스해야 합니다. HTTPS로 리다이렉트하면 무한 루프가 됩니다. `applyCloudflareTunnelLabels()`가 생성된 라벨을 바꿉니다.
  - **Traefik**: HTTPS 라우터를 `http` 엔트리포인트로 옮기고 TLS 라벨을 지웁니다. 미들웨어(접근 제한, Basic Auth 등)는 그대로 두고, 같은 규칙의 HTTP 라우터(리다이렉트용)는 지웁니다.
  - **Caddy**: 사이트 주소를 `http://host`로 바꿉니다.
- 앱이 원래 스킴(https)과 클라이언트 IP를 알 수 있도록, 터널이 켜져 있으면 프록시가 사설 대역에서 온 `X-Forwarded-*` 헤더를 믿습니다(Traefik `--entrypoints.http.forwardedheaders.trustedips=…`, Caddy `trusted_proxies static private_ranges`).
- 대시보드 도메인(설정의 인스턴스 도메인)도 터널 뒤에서는 HTTP로만 라우팅됩니다.
- 도메인 화면의 "DNS를 이 IP로" 안내와 자동 A 레코드 생성은 터널이 켜져 있으면 나오지 않습니다. DNS는 Cloudflare 터널이 관리합니다.

### 코드 위치

| 하는 일 | 파일 |
|---|---|
| cloudflared 시작/제거, 프록시 설정 반영 | `app/Actions/Server/ConfigureCloudflareTunnelIngress.php` |
| 화면 | `app/Livewire/Server/Proxy/CloudflareTunnelIngress.php` |
| 라벨 변환 | `bootstrap/helpers/proxy.php` `applyCloudflareTunnelLabels()` (`applyProxyEntryLabels()`가 와일드카드 인증서 다음에 호출) |
| 프록시 헤더 신뢰 설정 | `bootstrap/helpers/proxy.php` `applyCloudflareTunnelToProxyConfigArray()` |
| 테스트 | `tests/Feature/ControllerIngress/CloudflareTunnelIngressTest.php` |

기존 **서버 → Cloudflare Tunnel** 메뉴는 이와 별개로, 서버에 **SSH로 접속**할 때 터널을 쓰는 기능입니다.

## 문제 해결

| 증상 | 확인할 것 |
|---|---|
| 워커 앱 도메인이 404 | 컨트롤러에서 `docker ps --filter label=paded.relay=true`로 릴레이가 있는지 봅니다. 없으면 앱을 다시 배포하거나 프록시 페이지에서 **라우트 동기화**를 누릅니다. |
| 502 Bad Gateway | 컨트롤러에서 `nc -vz <워커 내부 IP> 41000`. 막혀 있으면 워커 방화벽에서 컨트롤러 → 41000-48999를 허용합니다. |
| 배포 시 "port is already allocated" | 워커에서 그 포트를 다른 프로그램이 쓰고 있습니다. 해당 프로그램을 옮기거나 다시 배포해 다른 포트를 받습니다. |
| 내부 IP를 바꿨는데 연결 안 됨 | 컨테이너는 예전 IP에 공개되어 있습니다. 워커의 앱을 다시 배포하고 서비스를 다시 시작합니다. |
| 터널 뒤에서 리다이렉트가 반복됨 | 터널을 켜기 전에 저장된 라벨일 수 있습니다. 앱을 다시 배포합니다(배포할 때 라벨을 다시 맞춥니다). 서비스는 다시 시작합니다. Cloudflare Public Hostname의 서비스가 `HTTP`, `coolify-proxy:80`인지 확인합니다. |
| 터널을 껐는데 HTTPS가 안 됨 | 라벨이 HTTP 전용으로 남아 있습니다. 앱의 라벨을 기본값으로 되돌리고(Reset labels) 다시 배포합니다. |
